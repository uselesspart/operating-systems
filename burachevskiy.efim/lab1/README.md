# Лабораторная работа № 1. Напоминалка

Вариант 19: демон на C++ проверяет события и открывает терминал с напоминанием. Одноразовые события и повторения каждый час, день или неделю. Интервал проверки по умолчанию — 10 секунд.

## Получение исходников

```bash
git clone --branch lab1-reminder https://github.com/R9quiem/operating-systems.git
cd operating-systems/burachevskiy.efim/lab1
```

Если первоначальная копия находится в `~/lab1-reminder`, она не является Git-клоном и сама не обновится. Её события можно сохранить отдельно и перенести в новую копию после проверки. Исходники и тесты из этой ветки не содержат пользовательского состояния и событий из Ubuntu.

## Сборка

Нужны Linux, Bash, g++ с поддержкой C++17 и графический терминал. В Ubuntu:

```bash
sudo apt install build-essential
chmod +x build.sh add_event test.sh
./build.sh
```

Сборка использует `-std=c++17 -Wall -Wextra -Werror -O2`. Результат — один файл `reminder`. Временный файл сборки удаляется автоматически; при ошибке прежний бинарник сохраняется. Первоначальная версия собиралась и проверяла конфигурацию в Ubuntu 26.04 с Ptyxis; окончательные изменения и тесты нужно проверить командой `./test.sh`. Для `pidfd` требуется Linux 5.3 или новее.

Программу запускают от обычного пользователя из терминала графического рабочего стола. `sudo` для запуска не нужен. При SSH без окружения графической сессии новое окно не появится.

## Первый запуск

Из папки проекта:

```bash
./reminder --check events.conf
./add_event "$(date -d '+1 minute' +%F)" "$(date -d '+1 minute' +%T)" "Проверка напоминания"
./reminder --foreground events.conf
```

Через минуту, с задержкой до интервала проверки, должно открыться новое окно с текстом. Enter закрывает напоминание. Ctrl+C останавливает программу в режиме переднего плана.

Для фонового режима:

```bash
./reminder events.conf
pid=$(head -n 1 events.conf.pid)
ps -p "$pid" -o pid,ppid,sid,tty,args
```

После успешного запуска приглашение командной строки возвращается. У демона в колонке TTY должно быть `?`. Исходное окно терминала можно закрыть. Графическая сессия пользователя должна оставаться открытой; выход из учётной записи и перезагрузка не входят в поддерживаемый сценарий.

## Конфигурация и события

Начальная конфигурация `events.conf`:

```text
interval=10
terminal=auto
```

`interval` задаётся в секундах от 1 до 3600. Для сдачи используется 10. Значение 1 удобно для коротких проверок.

`terminal=auto` ищет первый доступный терминал: Ptyxis, GNOME Terminal, GNOME Console (`kgx`), Konsole, XFCE Terminal, xterm. Можно указать имя или абсолютный путь поддерживаемого терминала, например `terminal=/usr/bin/ptyxis`.

Добавление событий:

```bash
./add_event 2026-11-01 18:30 "Одноразовое событие"
./add_event 2026-11-01 18:30 -h "Повтор каждый час"
./add_event 2026-11-01 18:30 -d "Повтор каждый день"
./add_event 2026-11-01 18:30 -w "Повтор каждую неделю"
```

Дата: `YYYY-MM-DD`. Время: `HH:MM` или `HH:MM:SS`. Используется местное время и часовой пояс, унаследованные при запуске. Допустимы годы 1970–2099. Текст — непустая строка без перевода строки и ESC. При ручном редактировании текст заключается в двойные кавычки, внутренние кавычки и обратные слеши экранируются обратным слешем.

Формат строки в файле:

```text
2026-11-01 18:30 - "Одноразовое событие"
2026-11-01 18:30 -d "Повтор каждый день"
```

В командной строке флаг необязателен. В самом файле для одноразового события обязательно указывается `-`. Пустые строки и строки, начинающиеся с `#`, игнорируются. Повторные директивы настроек отклоняются.

Скрипт `add_event` по умолчанию использует конфигурацию рядом с собой. Для другой конфигурации:

```bash
REMINDER_CONFIG=/home/efim/other.conf ./add_event 2026-11-01 18:30 "Другой список"
```

Сначала файл должен существовать и содержать корректную конфигурацию. Скрипт передаёт добавление тому же бинарнику через `--add`; отдельный компилятор или язык для добавления не требуется.

## Правила расписания

- Новые события обнаруживаются автоматически при очередной проверке файла.
- Проверяется условие «время уже наступило», поэтому событие не теряется между двумя проверками.
- Просроченное одноразовое событие показывается при запуске, если ещё не обработано.
- Для повторяющегося события после простоя показывается последнее наступившее срабатывание. Все пропущенные часы или дни отдельными окнами не воспроизводятся.
- `-h` означает каждые 3600 секунд. `-d` и `-w` используют календарные дни и сохраняют местное время суток. При переходе на летнее время несуществующее время повторения нормализует системная функция `mktime`; несуществующее исходное время в конфигурации отклоняется.
- Одинаковые строки считаются отдельными событиями. Ключ содержит время, тип повторения, текст и порядковый номер среди одинаковых записей. Изменение этих данных создаёт новое событие. Удаление одной из нескольких одинаковых строк может изменить их нумерацию.

Показ подтверждает процесс `reminder --show`: сначала он выводит текст, затем записывает подтверждение. Если терминал не запустился, завершился с ошибкой до подтверждения или подтверждение не пришло за 30 секунд, событие не помечается обработанным и будет повторено при следующей проверке. При уже открытом окне повторный запуск не выполняется, пока ожидается подтверждение.

Сохранение состояния выполняется после подтверждения, во временный файл с последующим `rename`. При аварийном выключении между выводом и сохранением возможен повтор напоминания: абсолютная гарантия «ровно один раз» для внешнего окна не заявляется.

## Сигналы, журнал, повторный запуск

Команды выполняются из папки проекта для того же конфигурационного файла:

```bash
kill -HUP "$(head -n 1 events.conf.pid)"
kill -TERM "$(head -n 1 events.conf.pid)"
journalctl -t reminder --since "10 minutes ago" --no-pager
```

`SIGHUP` немедленно прерывает ожидание и перечитывает конфигурацию. При ошибке сохраняется предыдущая корректная конфигурация, причина записывается в журнал. По `SIGTERM` демон выходит из цикла, пишет сообщение о завершении и освобождает PID-файл. `SIGINT` действует так же для удобства отладки. `SIGKILL` перехватить нельзя.

Повторная команда `./reminder events.conf` проверяет PID-файл, владельца и идентичность старого процесса через `/proc`, отправляет ему `SIGTERM` и ждёт освобождения блокировки. Затем записывает PID нового процесса после демонизации. После пересборки допускается замена процесса, исполняющего прежний удалённый inode бинарника по тому же пути. Для отправки сигнала используется `pidfd`, привязанный к конкретному процессу.

Первая строка PID-файла — PID. Следующие строки — время создания процесса из `/proc/PID/stat` и абсолютный путь конфигурации. Эти данные защищают от устаревшего PID и повторного использования его номера. Если PID-файл свободен, старое содержимое не служит основанием для отправки сигнала. Если занятый файл не прошёл проверку, программа завершится с ошибкой, не отправляя сигнал.

Есть дополнительный аргумент `--pid-file PATH` для отдельного размещения PID-файла. Для одной конфигурации во всех запусках нужно использовать один и тот же путь. По умолчанию это путь конфигурации с суффиксом `.pid`.

## Служебные файлы

| Файл | Назначение |
|---|---|
| `events.conf.pid` | PID, сведения о процессе и блокировка работающего экземпляра |
| `events.conf.pid.start.lock` | Блокировка одновременных попыток запуска |
| `events.conf.lock` | Согласование чтения и добавления событий |
| `events.conf.state` | Уже подтверждённые срабатывания |
| `events.conf.notify.*` | Временное подтверждение вывода напоминания |

При корректном завершении PID-файл остаётся пустым. Файлы блокировок специально не удаляются: удаление занятого файла позволило бы создать другой inode и обойти блокировку. Не удаляйте их, пока демон работает. Состояние сохраняется между запусками. Для повторной демонстрации проще добавить новое событие с другим текстом.

## Автоматические тесты

```bash
./test.sh
```

Все тесты и тестовый терминал написаны на C++. Внешние тестовые библиотеки, Python и установка дополнительных пакетов не нужны. Bash-скрипт только собирает и запускает тестовую программу. Для псевдотерминала используется стандартная библиотека Linux `libutil`.

Проверяются:

- корректные и ошибочные даты, високосный год, границы месяцев и годов;
- одноразовые события, все три повторения, календарное время при смене часового пояса на летнее;
- конфигурация, комментарии, CRLF, дубликаты, ошибки формата;
- добавление через настоящий скрипт, кавычки, русский текст, конкурентные добавления;
- PID-файл, блокировка, рабочая папка, стандартные потоки и отсутствие управляющего терминала;
- закрытие исходного псевдотерминала;
- одноразовый показ, передача буквального текста, подтверждение и отсутствие повторного показа после перезапуска;
- обнаружение новых событий, `SIGHUP`, сохранение прежней конфигурации после ошибки;
- `SIGTERM`, сообщения запуска и завершения через `syslog` с `LOG_PERROR` в режиме переднего плана;
- обычный повторный запуск и замена после пересборки;
- устаревший и поддельный PID-файл, сохранность постороннего процесса;
- ошибка терминала с последующей успешной повторной попыткой;
- повреждённое состояние и некорректные аргументы.

Расчёты дат проверяются с заданными временными метками без ожидания часов или недель. Интеграционные проверки используют интервал 1 секунду и изолированные каталоги в `/tmp`. Тестовый терминал записывает аргументы и запускает настоящий `reminder --show` с выводом в `/dev/null`; наличие графического сервера для этих тестов не требуется. Это проверяет протокол запуска и подтверждения, но не рисование окна настоящим Ptyxis.

Каждая проверка выводит `PASS` или `FAIL`. В конце — количество успешных и ошибочных проверок. При ошибке сохраняется каталог с диагностикой. Тесты не используют пользовательский `events.conf`, не останавливают пользовательский демон и не меняют настройки рабочего стола.

## Ручная проверка графического окна и журнала

1. Выполнить команды из раздела «Первый запуск», убедиться в правильном русском тексте и закрытии по Enter.
2. Остановить программу, добавить новое событие на минуту вперёд с другим текстом, запустить `./reminder events.conf`.
3. Закрыть исходный терминал и дождаться окна. После этого открыть новый терминал и перейти в папку проекта.
4. Проверить `ps` и записи через `journalctl -t reminder`.
5. Отправить `SIGTERM`, проверить отсутствие процесса и пустой PID-файл.

Если `--check` не находит терминал, проверить `command -v ptyxis` и значение `terminal`. Если терминал запускается, но окна нет, проверить графическую сессию и журнал. Значения `DISPLAY`, `WAYLAND_DISPLAY`, `DBUS_SESSION_BUS_ADDRESS`, `XDG_RUNTIME_DIR` наследуются от окружения запуска; код не подставляет произвольные адреса дисплея.

## Путь выполнения кода

`main.cpp` выбирает режим. `--add` вызывает `addEvent`, `--check` читает конфигурацию, `--show` выводит сообщение и подтверждает показ. Обычный запуск обращается к `Daemon::instance().run()`.

`run()` сохраняет абсолютные пути, открывает журнал, проверяет настройки, получает блокировки и устанавливает обработчики сигналов. Далее: первый `fork`, `setsid`, второй `fork`, `umask`, `chdir("/")`, перенаправление потоков и закрытие посторонних унаследованных дескрипторов. Второй `fork` оставляет демона вне роли лидера сеанса. Родитель получает сообщение о готовности по каналу и возвращает код успешного запуска.

`loop()` проверяет события и подтверждения показа. `latestOccurrence()` рассчитывает подходящее срабатывание. `notify()` создаёт дочерний процесс и запускает терминал через `execv`, передавая текст отдельным аргументом без shell. `waitpid` забирает завершившихся детей.

Обработчики сигналов устанавливают только флаги `volatile sig_atomic_t`. Основной код выполняет чтение файлов и журналирование. Сигналы блокируются при обработке данных и атомарно разрешаются на время `pselect`, чтобы не пропустить сигнал перед ожиданием.

Singleton ограничивает количество объектов класса внутри процесса. Блокировка PID-файла ограничивает количество работающих процессов для выбранного PID-файла. Эти механизмы выполняют разные задачи.
