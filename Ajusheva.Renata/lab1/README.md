# Лабораторная работа №1. Демон diskmond (вариант 20, Disk monitor)

> **Вариант 20.** Disk monitor. Отслеживать использование файлов в указанных в
> конфигурационном файле папках (inotify), записывать каждый акт взаимодействия
> в отдельный log-файл (настроить свой LOG_LOCAL0).

`diskmond` уходит в фон, ставит наблюдение `inotify` на каталоги из конфигурационного
файла (на каждый уровень вложенности) и на каждое действие с файлом — открыл, прочитал,
записал, закрыл, поменял права, создал, удалил, переименовал, перенёс — отправляет
одну строку в `syslog` с facility `LOG_LOCAL0`. Своё правило rsyslog складывает эти
строки в отдельный файл `/var/log/diskmond.log`. О себе (запуск, сигналы, ошибки,
остановка) демон пишет с facility `LOG_DAEMON` в обычный системный журнал.

## Как проверить за пять минут

```sh
./build.sh                                   # 1. сборка (или sh build.sh)
sudo sh scripts/setup_syslog.sh              # 2. один раз: LOG_LOCAL0 -> /var/log/diskmond.log

mkdir -p /tmp/diskmond-demo/docs /tmp/diskmond-demo/work
sudo ./diskmond                              # 3. запуск; конфиг — ./diskmond.conf

echo hello > /tmp/diskmond-demo/docs/a.txt   # 4. что-нибудь сделать с файлами
cat /tmp/diskmond-demo/docs/a.txt
sudo tail /var/log/diskmond.log              # 5. посмотреть журнал

sudo kill -TERM $(cat /run/diskmond.pid)     # 6. остановить
```

Запуск печатает, что взято, и возвращает управление, когда демон уже работает:

```
diskmond[28283]: launching in background: config /home/user/lab1/diskmond.conf, pid file /run/diskmond.pid
diskmond: running in background, pid 28285
```

В `/var/log/diskmond.log` после шагов 4–6:

```
... diskmond[28285]: <start> 2 directories under 2 roots
... diskmond[28285]: create      /tmp/diskmond-demo/docs/a.txt
... diskmond[28285]: open        /tmp/diskmond-demo/docs/a.txt
... diskmond[28285]: write       /tmp/diskmond-demo/docs/a.txt
... diskmond[28285]: close-write /tmp/diskmond-demo/docs/a.txt
... diskmond[28285]: open        /tmp/diskmond-demo/docs/a.txt
... diskmond[28285]: read        /tmp/diskmond-demo/docs/a.txt
... diskmond[28285]: close       /tmp/diskmond-demo/docs/a.txt
... diskmond[28285]: <stop>
```

А в `/var/log/syslog` — сообщения о самом демоне:

```
... diskmond[28285]: watching /tmp/diskmond-demo/docs (1 directory)
... diskmond[28285]: watching /tmp/diskmond-demo/work (1 directory)
... diskmond[28285]: up and running as pid 28285, 2 directories under 2 roots
... diskmond[28285]: SIGTERM from pid 28276: exiting
... diskmond[28285]: shutdown complete
```

## Сборка

```sh
./build.sh                  # или: sh build.sh
CXX=clang++ ./build.sh      # другим компилятором
```

Каждый `src/*.cpp` компилируется с `-std=c++17 -O2 -Wall -Wextra -Wpedantic -Werror`
(параллельно, по числу ядер), объектные файлы складываются во временный каталог
`mktemp -d`, из них собирается один `./diskmond`. Временный каталог удаляется всегда:
после удачной сборки, после ошибки компиляции и при Ctrl+C. Нужен `g++` (или `clang++`)
с C++17; проверено на g++ 9, 10, 11, 13 и clang 18.

## Журнал событий

Одна строка — одно действие:

```
<время> <хост> diskmond[<pid>]: <действие> <путь>[ -> <новый путь>]
```

Путь каталога заканчивается косой чертой (как в `ls -F`), так что файл и каталог
не спутать: `create /home/u/docs/` — создан каталог, `create /home/u/docs` — файл.

| действие      | из какого события inotify          | что случилось                                    |
|---------------|------------------------------------|--------------------------------------------------|
| `open`        | `IN_OPEN`                          | открыли                                          |
| `read`        | `IN_ACCESS`                        | прочитали (у каталога — список файлов)           |
| `write`       | `IN_MODIFY`                        | записали                                         |
| `close`       | `IN_CLOSE_NOWRITE`                 | закрыли; был открыт только для чтения            |
| `close-write` | `IN_CLOSE_WRITE`                   | закрыли; был открыт на запись                    |
| `attrib`      | `IN_ATTRIB`                        | поменяли права, владельца, время и т.п.          |
| `create`      | `IN_CREATE`                        | создали                                          |
| `delete`      | `IN_DELETE`                        | удалили                                          |
| `rename`      | `IN_MOVED_FROM` + `IN_MOVED_TO`    | переименовали на месте: `старый -> новый`        |
| `move`        | `IN_MOVED_FROM` + `IN_MOVED_TO`    | перенесли в другой наблюдаемый каталог           |
| `move-out`    | `IN_MOVED_FROM` без пары           | унесли туда, где наблюдения нет                  |
| `move-in`     | `IN_MOVED_TO` без пары             | принесли оттуда, где наблюдения нет              |
| `delete-self` | `IN_DELETE_SELF`                   | удалили сам каталог из конфигурации              |
| `move-self`   | `IN_MOVE_SELF`                     | переместили сам каталог из конфигурации          |
| `unmount`     | `IN_UNMOUNT`                       | файловую систему отмонтировали                   |

Отметки `<start>`, `<reload>`, `<stop>` и `<overflow>` показывают в том же журнале
запуск, перечитывание конфигурации, остановку и переполнение очереди inotify.
Управляющие символы в именах записываются как `\xNN`, а `\` — как `\\`: файл с
переводом строки в имени не подделает лишнюю запись в журнале.

Не записываются: чтение каталогов самим демоном при их обходе; повторы (о
подкаталоге inotify сообщает и родитель, и он сам); действия с файлом журнала
(`logfile`) и с путями из `ignore`.

## Свой LOG_LOCAL0

Правило `syslog/20-diskmond.conf`:

```
if $syslogfacility-text == "local0" and $programname == "diskmond" then {
    /var/log/diskmond.log
    stop
}
```

Оно забирает именно `local0` от `diskmond` (другие программы, которые тоже пишут
в `local0`, его не касаются), кладёт в `/var/log/diskmond.log` с теми же владельцем
и правами, что у остальных системных журналов, и останавливает дальнейшую обработку —
поэтому в `/var/log/syslog` эти строки не дублируются. Цифра 20 в имени — чтобы правило
стояло раньше стандартного `50-default.conf`.

```sh
sudo sh scripts/setup_syslog.sh            # поставить: копирует правило, проверяет конфигурацию
                                           # rsyslog, перезапускает его и шлёт пробную строку
sudo sh scripts/setup_syslog.sh --remove   # убрать
```

Вручную то же самое: `sudo cp syslog/20-diskmond.conf /etc/rsyslog.d/ && sudo systemctl restart rsyslog`.
Без systemd (WSL, контейнер) скрипт сам перезапускает `rsyslogd`. Если rsyslog не
установлен — `sudo apt install rsyslog`; в системе только с journald записи видны так:
`journalctl -t diskmond SYSLOG_FACILITY=16` (16 — это `local0`).

В Ubuntu rsyslog по умолчанию сворачивает *подряд идущие одинаковые* строки в одну
`message repeated N times: [...]` (например, много `write` одного файла при записи
большими порциями) — число повторов при этом сохраняется.

## Конфигурация

Без аргументов берётся `diskmond.conf` из текущего каталога; другой файл —
`./diskmond -c путь` или просто `./diskmond путь`. Путь сразу становится абсолютным
и запоминается: сам демон работает в `/`, но по SIGHUP перечитывает именно этот файл.

```
# каталоги для наблюдения
watch   /tmp/diskmond-demo/docs
watch = /tmp/diskmond-demo/work
ignore  /tmp/diskmond-demo/work/cache
logfile /var/log/diskmond.log
```

- `watch <каталог>` — наблюдать каталог со всеми подкаталогами; строк сколько угодно;
- `ignore <путь>` — не записывать действия с этим файлом или каталогом (и всем внутри);
- `logfile <файл>` — где лежит журнал LOG_LOCAL0 (по умолчанию `/var/log/diskmond.log`).
  Действия с ним не записываются никогда: иначе, окажись он в наблюдаемом каталоге,
  каждая запись в журнал порождала бы новую, и демон зациклился бы. Поэтому наблюдать
  можно даже `/var/log`.

Правила разбора: пустые строки и строки с `#` пропускаются; между словом и путём —
пробелы или `=`; регистр слова не важен; в пути могут быть пробелы; относительные пути
считаются от каталога, где лежит конфиг; символические ссылки раскрываются; повторы
и каталоги, вложенные в уже перечисленные, отбрасываются; CRLF и BOM от Windows
не мешают. О каждой непонятной строке (нет каталога, файл вместо каталога, неизвестное
слово) — предупреждение с номером строки в терминале и в системном журнале; остальные
строки работают.

## Управление демоном

```
./diskmond [-c CONFIG] [-p PIDFILE] [CONFIG]
./diskmond --help
```

Команда запуска не возвращает управление, пока демон не запишет pid-файл и не поставит
наблюдение: код 0 и `running in background, pid N` значат, что он действительно
работает, а при неудаче печатается причина (`startup failed: ...`) и код 1.

pid-файл: `/run/diskmond.pid` у root, `/tmp/diskmond-<uid>.pid` у обычного пользователя,
либо путь из `-p`.

```sh
sudo kill -HUP  $(cat /run/diskmond.pid)          # перечитать конфигурацию
sudo kill -TERM $(cat /run/diskmond.pid)          # остановить
sudo ./diskmond                                   # повторный запуск сам остановит прежний экземпляр
ps -o pid,ppid,pgid,sid,tty,stat,comm -C diskmond # убедиться, что процесс в фоне и без терминала
sudo grep diskmond /var/log/syslog                # сообщения о демоне (или journalctl -t diskmond)
sudo tail -f /var/log/diskmond.log                # журнал событий
```

**SIGHUP** — конфигурация перечитывается: каталоги, которых больше нет в файле,
отпускаются, новые добавляются, а те, что не менялись, наблюдаются без перерыва.
Если файл не читается, остаются прежние настройки. **SIGTERM** — в системный журнал
пишется `SIGTERM from pid N: exiting`, дописываются события, случившиеся до сигнала,
удаляется свой pid-файл, и последняя запись — `shutdown complete`.

## Устройство

**Уход в фон** (`Daemonize.cpp`). До `fork()` программа находит и читает конфиг
в рабочем каталоге (запоминая абсолютный путь) и разбирается с прежним экземпляром.
Затем: `fork()`, причём родитель не завершается сразу, а ждёт отчёта по каналу (pipe);
`setsid()` — новый сеанс без управляющего терминала; второй `fork()` — процесс больше
не лидер сеанса и не сможет снова получить терминал; `umask(0)`; `chdir("/")`;
закрываются все унаследованные дескрипторы (по списку `/proc/self/fd`), а 0, 1, 2
направляются в `/dev/null`; syslog открывается заново. Потом сигналы, pid-файл
(pid уже самого демона), наблюдение — и отчёт «готов» по каналу.

**Синглтон.** Класс `Daemon` существует в одном экземпляре: объект создаётся внутри
`Daemon::instance()`, конструктор закрыт, копирование и перемещение запрещены.

**Сигналы.** SIGHUP и SIGTERM заблокированы и читаются из `signalfd` в том же `poll()`,
где ждутся события inotify. Так сигнал обрабатывается в основном цикле, а не в
асинхронном обработчике: он не прерывает работу на полпути и не теряется между
проверкой флага и ожиданием; заодно известно, какой процесс его прислал. Пока ничего
не происходит, демон спит в `poll()` — никакого интервала опроса нет.

**Один экземпляр.** Новый процесс читает pid из pid-файла и смотрит в `/proc/<pid>`:
каталога нет или процесс — зомби → файл устарел; процесс есть, но это другая программа
(сверяются `/proc/<pid>/comm` и имя файла по ссылке `/proc/<pid>/exe`) → его не трогаем,
ведь после сбоя pid мог достаться кому угодно; это diskmond → ему отправляется SIGTERM,
и новый процесс ждёт, пока тот завершится. Свой pid демон пишет после ухода в фон,
атомарно (временный файл и `rename()`, без перехода по символическим ссылкам), а при
выходе удаляет файл, только если в нём всё ещё его pid.

**Наблюдение на всю глубину.** inotify видит один каталог без вложенных, поэтому
наблюдение ставится на каждый подкаталог. В `WatchTree` у каждого наблюдения хранятся
только родитель и имя, полный путь собирается при записи — переименование каталога
меняет один узел, и пути всего, что внутри, сразу верные.
- На новый каталог наблюдение ставится до того, как его прочитать: появившееся после
  придёт событием, появившееся до — найдёт обход. Всё, что обход нашёл в *только что
  созданном* каталоге, тоже только что создано, просто inotify не успел это увидеть
  (`mkdir -p a/b/c`, `cp -r`) — это записывается как `create`.
- Сам обход порождает события `open/read/close` каталога. Перед обходом демон забирает
  из очереди ядра всё, что там уже есть, и узнаёт свои события по номеру в общем потоке —
  поэтому они не путаются с действиями пользователя.
- `IN_MOVED_FROM` ждёт пары `IN_MOVED_TO` с тем же cookie: нашлась — это `rename` или
  `move`, и наблюдение переезжает вместе с каталогом; не нашлась — `move-out`,
  наблюдение снимается; `IN_MOVED_TO` без пары — `move-in`, каталог обходится.
- При переполнении очереди (`IN_Q_OVERFLOW`) все деревья обходятся заново.
- За один проход обрабатывается ограниченная порция событий, так что и под непрерывным
  потоком событий сигналы обрабатываются сразу.

## Тесты

```sh
./tests/run_all.sh                    # всё (или: bash tests/run_all.sh)
./tests/run_all.sh unit signals       # выборочно: unit или часть имени сценария
sudo ./tests/run_all.sh               # плюс проверка с настоящим rsyslog
```

Нужны `bash` и `g++`. `run_all.sh` собирает проект через `build.sh`, модульные тесты и
вспомогательную библиотеку — во временный каталог, который потом удаляет.

Сценарии в `tests/integration/` запускают настоящий демон (fork, setsid, inotify,
сигналы, pid-файл), каждый в своём временном каталоге и со своим pid-файлом, поэтому
работающий в системе diskmond они не задевают. Подменяется только `syslog()`: библиотека
`tests/preload/syslog_capture.cpp` через `LD_PRELOAD` дописывает каждое сообщение вместе
с его facility в файл сценария. Так тесты проверяют, что записи о файлах идут именно с
`LOG_LOCAL0`, а сообщения о демоне — с `LOG_DAEMON`, и при этом не требуют ни root, ни
rsyslog. Цепочку через настоящий rsyslog проверяет `10_rsyslog.sh` — ему нужны root и
установленное правило, без них он пропускается и объясняет почему.

- `unit` — пути, разбор конфигурации, дерево наблюдений, формат записей, pid-файл, проверки `/proc`;
- `01_build` — один исполняемый файл, `-Wall -Werror`, предупреждение валит сборку, временные файлы
  не остаются ни после ошибки, ни после прерывания, сборка через clang++;
- `02_daemonize` — фон и код возврата, нет терминала, свой сеанс, не лидер сеанса и группы, `/`,
  `/dev/null`, закрыты унаследованные дескрипторы, umask, нет расхода процессора без событий;
- `03_config` — конфиг из каталога запуска, `-c` и аргумент, относительные пути, разбор строк,
  предупреждения с номерами строк, ошибки;
- `04_file_events` — запись, чтение, дописывание, `ls`, атрибуты, `rename`/`move`/`delete`,
  `move-out`/`move-in`, ссылки, две facility, необычные имена;
- `05_subdirectories` — глубокое дерево, новые каталоги, `mkdir -p`, `cp -r`, никаких повторов,
  обход не попадает в журнал, переименование и перенос каталогов, удаление и перемещение корня,
  символические ссылки;
- `06_signals` — SIGHUP добавляет и убирает каталоги, не прерывает наблюдение, переживает пропавший
  конфиг и серию сигналов; SIGTERM — сообщение о выходе, pid-файл удалён;
- `07_single_instance` — повторный запуск останавливает прежний; устаревший pid; чужой процесс;
  процесс, назвавшийся diskmond; мусор в pid-файле; чужой pid-файл не удаляется; ошибка записи;
- `08_filters` — журнал LOG_LOCAL0 в наблюдаемом каталоге не зацикливает демон; `ignore`;
  перемещения через границу `ignore`;
- `09_stress` — 1000 файлов и 200 деревьев каталогов без потерь; SIGTERM под потоком событий;
- `10_rsyslog` — настоящий rsyslog: записи о файлах в `/var/log/diskmond.log`, о демоне —
  в `/var/log/syslog`, без дублей.
