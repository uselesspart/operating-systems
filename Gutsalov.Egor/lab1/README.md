# Лабораторная работа № 1. Процессы и демонизация

**Гуцалов Егор, 5030102/30201 вариант 13 — сборщик логов**

Программа на C++20 работает как демон Linux. Каждые 45 секунд она дописывает
содержимое файлов `*.log` из первого каталога в `total.log` второго каталога,
а затем удаляет успешно обработанные исходники. Каталоги и интервал задаются
в конфигурационном файле.

## Требования и сборка

Нужны Linux с `/proc`, компилятор с поддержкой C++20 (например, GCC 11+),
CMake 3.20+, Make и Bash. Для тестов дополнительно нужен Python 3.8+.
Скачивание библиотек и права root не требуются.

Все команды ниже выполняются из `Gutsalov.Egor/lab1`:

```bash
./build.sh
```

Результат — один исполняемый файл `./lab1`. Компиляция идёт с
`-Wall -Wextra -Werror`. Скрипт собирает проект во временном каталоге и удаляет
его при успешном завершении и при ошибке. Бинарник заменяется через переименование,
поэтому сборку можно выполнять и при работающем демоне.

Для разработки можно оставить CMake-сборку:

```bash
cmake -S . -B build -DRELEASE=OFF -DENABLE_TESTING=ON
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Бинарник в этом случае находится в `build/bin/lab1`. Сборка из родительского
каталога `Gutsalov.Egor` также поддерживается его `CMakeLists.txt`.

### Параметры сборки и санитайзеры

Одни и те же булевы параметры поддерживаются CMake и обоими скриптами:

| Параметр | Значение |
| --- | --- |
| `RELEASE` | `ON` выбирает Release, `OFF` — Debug; задаёт `CMAKE_BUILD_TYPE` |
| `ENABLE_TESTING` | Собрать тесты и включить CTest |
| `ENABLE_ASAN` | Инструментировать код AddressSanitizer для поиска ошибок памяти |
| `ENABLE_TSAN` | Инструментировать код ThreadSanitizer для поиска гонок данных |

По умолчанию `build.sh` использует `RELEASE=ON`, `ENABLE_TESTING=OFF`;
`run_tests.sh` — `RELEASE=OFF`, `ENABLE_TESTING=ON`. Оба санитайзера выключены.
У CMake по умолчанию Debug и включённые тесты; если при первой конфигурации
передан `CMAKE_BUILD_TYPE=Release`, начальное значение `RELEASE` будет `ON`.
При дальнейшем конфигурировании приоритет имеет явный параметр `RELEASE`.

Скрипты принимают `-DИМЯ=ЗНАЧЕНИЕ`, `ИМЯ=ЗНАЧЕНИЕ` и переменные окружения.
Аргумент командной строки имеет приоритет над окружением. Значения: `ON/OFF`,
`TRUE/FALSE`, `YES/NO`, `1/0` без учёта регистра.

```bash
# Release: собрать, проверить и только после успешных тестов заменить ./lab1.
./build.sh -DRELEASE=ON -DENABLE_TESTING=ON

# Независимые Debug-прогоны с санитайзерами.
./run_tests.sh -DENABLE_ASAN=ON
./run_tests.sh -DENABLE_TSAN=ON

# Те же параметры через окружение или без префикса -D.
ENABLE_ASAN=ON RELEASE=OFF ./run_tests.sh
./build.sh RELEASE=OFF ENABLE_TESTING=ON ENABLE_ASAN=ON

# Аргументы CTest можно передать после --; прежний ./run_tests.sh -V тоже работает.
./run_tests.sh -DENABLE_TSAN=ON -- -V
./build.sh --help
```

`build.sh ENABLE_TESTING=ON` запускает CTest до установки бинарника.
`run_tests.sh` требует включённых тестов: при `ENABLE_TESTING=OFF` он завершится
с ошибкой и предложит использовать `build.sh`.

ASan и TSan взаимно исключаются: включение обоих отклоняется скриптами и CMake.
Для них нужны GCC/Clang и соответствующие библиотеки исполнения. Флаги
`-fsanitize=address` или `-fsanitize=thread` применяются при компиляции и линковке;
добавляются `-g` и `-fno-omit-frame-pointer`. Инструментируются основной код,
исполняемые файлы тестов и перехватчик журнала. Параметр `RELEASE` независим от
санитайзеров. Флаги `-Wall -Wextra -Werror` сохраняются во всех режимах.

Для сохранения отдельных сборок:

```bash
cmake -S . -B build-asan -DRELEASE=OFF -DENABLE_TESTING=ON -DENABLE_ASAN=ON
cmake --build build-asan --parallel
ctest --test-dir build-asan --output-on-failure

cmake -S . -B build-tsan -DRELEASE=OFF -DENABLE_TESTING=ON -DENABLE_TSAN=ON
cmake --build build-tsan --parallel
ctest --test-dir build-tsan --output-on-failure
```

На Linux ASan обычно также включает LeakSanitizer. Если среда запрещает ему
проверять потоки и он сообщает `LeakSanitizer does not work under ptrace`,
проверки адресов можно запустить отдельно:

```bash
ASAN_OPTIONS=detect_leaks=0 ./run_tests.sh -DENABLE_ASAN=ON
```

В таком прогоне **утечки памяти не проверяются**. Скрипты сами не отключают
санитайзеры, не подавляют их отчёты и не повторяют упавшие проверки до успеха.

## Конфигурация

По умолчанию программа ищет `lab1.conf` в рабочем каталоге запуска. Пример уже
лежит в репозитории:

```ini
# Относительные пути отсчитываются от каталога конфигурационного файла.
source_dir = data/source
target_dir = data/archive
interval = 45
```

Все три параметра обязательны. `interval` — целое число секунд от 1 до
2147483647; для варианта 13 используется **45**. Оба каталога должны существовать
и различаться. Неизвестные и повторяющиеся ключи, пустые значения и неверные
пути считаются ошибкой. Поддерживаются пустые строки, комментарии отдельной
строкой с `#`, CRLF и пробелы внутри путей. Кавычки, подстановка `$HOME` и `~`
не используются.

Путь к конфигу переводится в абсолютный до демонизации. После перехода демона
в `/` перечитывание продолжает работать. Файл можно редактировать или заменять
атомарно по тому же пути.

## Запуск и управление

```bash
mkdir -p data/source data/archive
printf 'Первая запись\nВторая запись\n' > data/source/example.log
./lab1
cat data/archive/total.log
```

Первый проход выполняется сразу после запуска, следующие — через `interval`
секунд после завершения предыдущего. Родительский процесс возвращает код `0`
только после готовности демона и записи его PID. Ошибки обработки файлов
регистрируются отдельно; демон продолжает работать и повторяет попытку на
следующем проходе.

Другой конфиг и отдельный PID-файл можно передать явно:

```bash
./lab1 /absolute/path/to/lab1.conf --pid-file /tmp/my-lab1.pid
```

Стандартный PID-файл — `/tmp/gutsalov-lab1-<UID>.pid`, где UID — идентификатор
эффективного пользователя. Все экземпляры, использующие один PID-файл,
заменяют друг друга. `--pid-file` позволяет изолировать тестовый экземпляр.

Скрипт управления принимает действие, необязательный путь к конфигу и
необязательный путь к PID-файлу. Его стандартный конфиг — `lab1.conf` рядом с
бинарником, поэтому скрипт можно вызывать из другого каталога:

```bash
./scripts/control.sh start
./scripts/control.sh status
./scripts/control.sh reload
./scripts/control.sh restart
./scripts/control.sh stop

# Управление экземпляром с нестандартными путями:
./scripts/control.sh status /absolute/path/to/lab1.conf /tmp/my-lab1.pid
```

Те же сигналы вручную:

```bash
kill -HUP "$(cat "/tmp/gutsalov-lab1-$(id -u).pid")"
kill -TERM "$(cat "/tmp/gutsalov-lab1-$(id -u).pid")"
```

- `SIGHUP`: прочитать конфиг, проверить его целиком и применить новые каталоги
  и интервал; сразу выполнить проход. Если конфиг неверный или исчез,
  записать ошибку в syslog и продолжить со старыми настройками.
- `SIGTERM`: закончить текущий проход, записать сообщение о выходе в syslog,
  очистить PID-файл и освободить блокировку.
- Повторный запуск: прочитать PID-файл, проверить `/proc/<PID>` и принадлежность
  процесса этой программе, отправить старому демону `SIGTERM`, дождаться
  освобождения блокировки и записать PID нового процесса после демонизации.
  Ожидание ограничено 10 секундами. Неверный конфиг нового запуска не
  останавливает уже работающий экземпляр.

PID-файл остаётся пустым после штатной остановки: сохранение его inode исключает
гонку при блокировке через `flock`. Устаревший или испорченный PID обрабатывается
при следующем запуске. Если PID принадлежит другой программе, запуск отклоняется
без отправки ей сигнала. Не удаляйте PID-файл работающего демона.

### Безопасность обработки сигналов

В программе нет `std::signal`, `sigaction`-обработчиков и разделяемых с ними
переменных. `SIGHUP` и `SIGTERM` блокируются через `sigprocmask` **до первого
`fork`**, маска наследуется обоими потомками. Демон получает уведомления через
`signalfd` и `poll`, затем читает конфиг, работает с файлами и вызывает syslog
в обычном основном цикле. Эти операции не выполняются в асинхронном обработчике.

Для асинхронного обработчика недостаточно обычной потокобезопасности: нужна
async-signal-safety. Синхронное получение сигналов через `signalfd` позволяет
не вызывать небезопасные для обработчика функции. Если в сам демон будут
добавляться потоки, эти сигналы нужно блокировать в исходном потоке **до их
создания**, чтобы все потоки унаследовали маску. Подробнее:
[signalfd(2)](https://man7.org/linux/man-pages/man2/signalfd.2.html) и
[signal-safety(7)](https://man7.org/linux/man-pages/man7/signal-safety.7.html).

Для одного прохода без демонизации, PID-файла и ожидания:

```bash
./lab1 lab1.conf --once
./lab1 --help
```

`--once` возвращает `0`, если проход завершился без ошибок, и `1` при ошибке.
Используйте его при остановленном демоне для тех же каталогов.

## Формат результата и работа с файлами

Для каждого исходника добавляется последовательность байтов:

```text
\n\n<имя файла>\n\n<содержимое исходника>
```

То есть перед именем добавляются два перевода строки, после имени — перевод
строки и ещё одна пустая строка. Содержимое сохраняется побайтно, включая
нулевые байты и отсутствие завершающего перевода строки. Старое содержимое
`total.log` сохраняется. Порядок обработки — по возрастанию пути.

Сохранён рекурсивный обход из начальной реализации. Для вложенного файла
в заголовке используется путь относительно первого каталога, например
`service/error.log`. Обрабатываются только обычные файлы с окончанием `.log`
с учётом регистра. Каталоги, FIFO и символические ссылки пропускаются;
символические ссылки на каталоги не обходятся. Сам выходной `total.log` и
его жёсткие ссылки пропускаются, даже если второй каталог вложен в первый.

Копирование идёт блоками по 64 КиБ. Исходник удаляется только после успешного
чтения, записи и `fsync` результата. При ошибке копирования программа пытается
вернуть `total.log` к прежнему размеру, оставляет исходник и сообщает об ошибке.
Изменение размера, времени модификации или подмена исходника во время копирования
также приводят к отказу от удаления. Символическая ссылка вместо `total.log`
отклоняется.

Для предсказуемого результата подавайте закрытые логи, которые уже не изменяются.
Запись результата и удаление исходника не являются одной атомарной операцией:
при аварийной остановке между ними или ошибке удаления возможна повторная запись
на следующем проходе. Откат при ошибке записи также может не удаться при сбое
файловой системы. Экземпляры с разными PID-файлами должны работать с разными
исходными каталогами.

## Системный журнал

Используются `openlog`, `syslog`, `closelog`; идентификатор — `gutsalov-lab1`,
facility — `LOG_DAEMON`. Записываются запуск, завершение по `SIGTERM`, ошибки,
результат перечитывания конфигурации и число обработанных файлов.

На системе с journald:

```bash
journalctl -t gutsalov-lab1 -f
```

Если установлен rsyslog с обычными правилами:

```bash
grep gutsalov-lab1 /var/log/syslog
```

Доступ к журналу зависит от настроек системы. В минимальном контейнере без
`/dev/log` сообщения syslog некому принимать; для их просмотра нужен системный
логгер. `total.log` содержит только данные исходных логов.

## Тесты

```bash
./run_tests.sh
./run_tests.sh -V
```

Скрипт собирает тесты и программу с `-Wall -Wextra -Werror`, запускает CTest
и удаляет временную сборку. Каждый сценарий использует собственные каталоги
в `/tmp` и PID-файл. Запущенные демоны останавливаются и собираются через
`waitpid`; права root, Docker и сторонние Python-пакеты не нужны.

Проверки:

- C++: единственность объекта `Daemon`, включая одновременное первое обращение
  из восьми тестовых потоков; запрет обычного создания и копирования.
- Python: точный формат, сохранение существующего результата, пустые и бинарные
  файлы, рекурсия, Unicode, ссылки, специальные файлы, исключение самого результата.
- Ошибки вывода и откат частичной записи при ограничении `RLIMIT_FSIZE`.
- Разбор конфигурации, относительные пути, CRLF, неверные ключи и интервалы.
- Настоящая демонизация: отдельный сеанс, отсутствие управляющего терминала,
  рабочий каталог `/`, `/dev/null` на дескрипторах 0–2, закрытие унаследованных
  дескрипторов и маска доступа `0077`.
- Периодические проходы, `SIGHUP`, сохранение настроек при ошибке перечитывания,
  `SIGTERM`, повторный запуск и восстановление после `SIGKILL`; маска сигналов
  через `/proc` и серия сигналов во время заблокированной записи в результат.
- Повреждённый, устаревший, чужой PID и символическая ссылка вместо PID-файла.
- Сообщения syslog, повторная попытка после ошибки и все действия `control.sh`.
- Параметры скриптов и их приоритет, передача аргументов CTest, смена Debug/Release
  в CMake из родительского каталога и отклонение несовместимых санитайзеров.

Интеграционный драйвер компилируется из тех же `main.cpp` и `lab1_core`, что
рабочая программа. Только вызовы `openlog`, `syslog`, `closelog` заменены
реализациями из `tests/syslog_capture.cpp`, которые пишут в тестовый файл.
Это позволяет обойтись без `LD_PRELOAD`, конфликтующего с порядком загрузки
санитайзеров. Перехватчик не входит в рабочий бинарник; для него также есть
отдельная проверка запуска CLI. Проверяется вызов API, а доставка в
journald/rsyslog зависит от системного логгера.

В тестах `ASAN_OPTIONS` и `TSAN_OPTIONS` дополняются параметром `log_path`:
отчёты всех процессов, включая фоновый демон с перенаправленным `stderr`,
проверяются после остановки. Любой непустой отчёт или неожиданный код завершения
демона проваливает тест. Финальный демон использует `std::exit`, чтобы выполнить
завершающие проверки санитайзеров; промежуточный процесс после второго `fork`
по-прежнему использует `_exit`.

Успешный TSan-прогон проверяет выполненные сценарии, а не доказывает отсутствие
всех возможных гонок. Сам демон остаётся однопоточным; восемь потоков создаёт
только отдельный тест singleton. Описание инструментов:
[AddressSanitizer](https://clang.llvm.org/docs/AddressSanitizer.html),
[ThreadSanitizer](https://clang.llvm.org/docs/ThreadSanitizer.html).
