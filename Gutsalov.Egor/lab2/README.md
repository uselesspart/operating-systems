# Лабораторная №2: межпроцессное взаимодействие

Реализован **вариант 20 (20 баллов)** из
[условия](../../2.%20Межпроцессное%20взаимодействие/lab2.md): локальный чат,
независимые процессы, один хост и несколько клиентов, отдельный поток на клиента.
Все три транспорта реализованы: анонимные каналы `pipe`, именованные каналы
`fifo` и Unix-сокеты `sock`. Хост и клиенты имеют интерфейс Qt Widgets.

## Зависимости и сборка

Нужны Linux с glibc 2.30+, CMake 3.20+, компилятор C++20, Qt 5 или Qt 6 Widgets
и Python 3 для тестов. В Ubuntu зависимости можно установить так:

```bash
sudo apt-get install build-essential cmake qtbase5-dev python3
```

Сборка устроена по образцу `../lab1`: CMake работает во временном каталоге,
скрипты удаляют его при завершении, включая ошибки и сигналы. Исполняемые файлы
устанавливаются рядом с `build.sh`, после успешных тестов, если они включены.
Замена каждого бинарника атомарная, поэтому можно собирать новую версию,
пока работает предыдущая.

```bash
cd Gutsalov.Egor/lab2
./build.sh                       # Release, без тестов
./build.sh ENABLE_TESTING=ON     # Release, с тестами
./run_tests.sh                   # Debug, все тесты
./run_tests.sh -- -V -R unit     # только модульные тесты
make                            # собрать все host_* и client_*
make test
```

Поддерживаются те же переключатели, что в первой лабораторной:

| Параметр | `build.sh` | `run_tests.sh` | Значение |
| --- | --- | --- | --- |
| `RELEASE` | `ON` | `OFF` | `ON` — Release, `OFF` — Debug |
| `ENABLE_TESTING` | `OFF` | `ON` | Сборка и запуск тестов |
| `ENABLE_ASAN` | `OFF` | `OFF` | AddressSanitizer |
| `ENABLE_TSAN` | `OFF` | `OFF` | ThreadSanitizer |

Можно передавать `KEY=VALUE`, `-DKEY=VALUE` или переменные окружения.
Аргументы командной строки имеют приоритет. ASan и TSan включаются отдельно.
`run_tests.sh ENABLE_TESTING=OFF` отклоняется. Во всех режимах используются
`-Wall -Wextra -Werror`.

```bash
./run_tests.sh -DENABLE_ASAN=ON
RELEASE=OFF ./build.sh
CTEST_PARALLEL_LEVEL=4 ./run_tests.sh
```

`CMAKE_BUILD_PARALLEL_LEVEL` задаёт число параллельных задач сборки (по умолчанию
2). `CTEST_PARALLEL_LEVEL` задаёт параллельность тестов. Для Qt в нестандартном
каталоге используйте `CMAKE_PREFIX_PATH`; библиотеки и плагины должны быть
доступны загрузчику Qt и Linux.

Обычная сохраняемая сборка тоже поддерживается, в том числе из
`Gutsalov.Egor/CMakeLists.txt` вместе с первой лабораторной:

```bash
cmake -S . -B build -DRELEASE=OFF -DENABLE_TESTING=ON
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure --parallel 4
# Программы: build/bin/{host,client}_{pipe,fifo,sock}
```

## Запуск

Сначала запускается хост. PID виден в заголовке окна и в строке
`READY host <PID> <транспорт>` в терминале. Затем запускаются независимые
клиенты с этим PID. В одной сессии используется один и тот же транспорт:

```bash
./host_pipe
# В других терминалах, вместо 12345 подставить PID хоста:
./client_pipe 12345
./client_pipe 12345
```

Для FIFO и сокетов аналогично используются `host_fifo` / `client_fifo` и
`host_sock` / `client_sock`. Процессы должны работать от одного пользователя.

В поле «Адресат» укажите `-1` для общего чата, `0` для хоста или PID клиента
для личного сообщения. Список PID выводится при подключении; подключения,
выходы и ошибки появляются в истории и строке состояния. Отправка — кнопкой
или Enter. Допустим текст длиной 1–1024 байта UTF-8 без переводов строк и NUL.
Разметка в сообщениях отображается как обычный текст.

Для работы без графического дисплея есть режим `--headless`. Он использует
тот же протокол, маршрутизацию и системные вызовы IPC:

```bash
./host_sock --headless
./client_sock 12345 --headless
```

Команды на стандартном вводе:

```text
Сообщение всем участникам
/to 12346 Личное сообщение клиенту 12346
/to 0 Личное сообщение хосту
/quit
```

EOF стандартного ввода прекращает его чтение; процесс продолжает принимать
сообщения. Для остановки используются `/quit`, закрытие окна, `SIGINT` или
`SIGTERM`. При остановке хоста клиенты обнаруживают закрытие соединения и
завершаются. События дублируются в stdout, ошибки запуска — в stderr.

## Как устроено взаимодействие

1. Хост создаёт собственный каталог `/tmp/gutsalov-lab2-<UID>-<PID>` с правами
   `0700`. До создания потоков блокируются сигналы; асинхронных обработчиков нет.
2. Клиент отправляет `SIGUSR1`. Хост получает PID и UID отправителя через
   `signalfd`, создаёт отдельный поток, транспорт и четыре именованных семафора
   через `sem_open`. Когда ресурсы готовы, отправляет `SIGUSR2` через `sigqueue`.
   Клиент синхронно ждёт подтверждение через `sigtimedwait` и проверяет PID, UID
   и переданный идентификатор. Идентификатор клиента равен его PID.
3. Повторная отправка запроса каждые 200 мс компенсирует слияние обычных сигналов
   при одновременном подключении. Общий срок знакомства — 5 секунд.
4. Каждое направление связи имеет семафор свободного слота и семафор готового
   сообщения. Отправитель занимает слот, записывает кадр и сообщает о готовности;
   получатель читает кадр и освобождает слот. `sem_clockwait` использует
   `CLOCK_MONOTONIC` и тайм-аут 5 секунд. Активные операции чтения, записи,
   подключения и передачи дескрипторов также ограничены 5 секундами.
5. Плановое ожидание пользовательского ввода или следующего сообщения не
   разрывает соединение через 5 секунд. Если клиент не отправлял сообщения
   60 секунд, хост завершает его `SIGKILL` через `pidfd_send_signal`. `pidfd`
   сохраняет привязку к процессу и исключает отправку сигнала повторно
   использованному PID. Хост освобождён от ограничения неактивности.
6. Хост маршрутизирует общие сообщения всем участникам, личные — только
   отправителю и адресату. Личные сообщения двух клиентов не выводятся у хоста.
   У каждого клиента отдельная ограниченная очередь отправки, поэтому
   не читающий участник не блокирует общий диспетчер.

Транспорты имеют один интерфейс `Connection` / `Channel`:

| Файл | Передача сообщений |
| --- | --- |
| `src/conn_pipe.cpp` | Два настоящих анонимных канала `pipe2` |
| `src/conn_fifo.cpp` | Два FIFO, созданных `mkfifo` |
| `src/conn_sock.cpp` | Двунаправленный Unix stream socket |

Независимый процесс не наследует дескрипторы `pipe`. Поэтому для этого варианта
хост передаёт клиентские концы каналов через короткое служебное соединение
Unix-сокета с `SCM_RIGHTS`. В FIFO-варианте служебный сокет проверяет PID/UID
через `SO_PEERCRED` и согласует открытие концов. В обоих случаях сообщения чата
проходят исключительно через выбранные каналы. В сокетном варианте сообщения
проходят через сам Unix-сокет.

Кадр содержит длину и проверяемый заголовок; PID отправителя хост берёт из
соединения, а не доверяет полю запроса. Счётчик `sequence` задаёт единый порядок
доставки. Для времён отправки используется `system_clock` в наносекундах;
диспетчер сортирует сообщения с буфером переупорядочивания 150 мс. Времена
доставленных сообщений не убывают. Сообщение, пришедшее после этого окна и
оказавшееся раньше уже доставленного, отклоняется с уведомлением отправителя.
Резкое изменение системного времени также может привести к отклонению сообщения.
Равные времена сохраняют порядок приёма. Это ограничение относится к порядку
чата; тайм-ауты и проверка неактивности используют монотонные часы.

Дескрипторы закрываются через RAII. После отключения клиента хост удаляет его
FIFO, сокеты и имена семафоров; завершившиеся потоки собираются и удаляются.
После штатной остановки хоста удаляется каталог сессии. `SIGKILL` самого хоста
не позволяет выполнить деструкторы; в таком случае могут остаться его файлы IPC.

## Автоматическая сборка исходников

CMake находит `src/*.cpp`, `src/*.c` и `src/conn_*` через
`GLOB_RECURSE CONFIGURE_DEPENDS`. Новые исходники попадают в сборку без правки
списков. Каждый `conn_<code>.cpp` с реализацией общего интерфейса автоматически
создаёт пару `host_<code>` и `client_<code>`. Точки входа находятся в `host.cpp`
и `client.cpp`. Команда `make` в папке лабораторной запускает `build.sh` и
собирает все пары; промежуточные файлы CMake удаляются.

## Тесты

CTest содержит модульные тесты C++ и компонентные сценарии Python без сторонних
пакетов. Все процессы запускаются из собранных рабочих бинарников; для IPC
не используются заглушки. Тестам необходимы Unix-сокеты, именованные семафоры
и возможность посылать сигналы собственным дочерним процессам.

Проверяются:

- Протокол: точное восстановление полей, UTF-8, границы размера, неверные
  заголовки, запрет NUL/переводов строк и правила видимости личных сообщений.
- Потокобезопасная очередь событий: восемь производителей, 800 записей.
- Аргументы программ и параметры сборки, их приоритет и несовместимые режимы.
- Для каждого транспорта: общий чат, все направления личных сообщений,
  сообщение самому себе, неизвестный адресат, сохранение соединения после
  неверного ввода, одинаковый порядок сообщений у всех участников.
- Восемь одновременных подключений, повторное подключение, аварийное завершение
  клиента, остановка хоста, освобождение файлов сессии и именованных семафоров.
- Настоящие окна Qt: запуск и получение сообщений без дисплея с платформенным
  плагином `minimal`. Он позволяет проверять утечки под ASan, в отличие от
  `offscreen` в использованной Qt 5.15, который сохраняет выделенный `QScreen`.
- Реальные пятисекундные тайм-ауты: остановленный хост при знакомстве,
  остановленный клиент при ожидании семафора свободного слота.
- Реальные 60 секунд неактивности сразу на трёх транспортах: молчащие клиенты
  получают `SIGKILL`, клиенты, отправившие сообщение в середине минуты, продолжают
  работать, хосты также остаются запущенными.

Набор содержит один минутный сценарий, поэтому полный прогон занимает не менее
минуты. С `CTEST_PARALLEL_LEVEL=4` остальные сценарии выполняются параллельно
с ним. Код завершения каждого процесса проверяется; отчёты санитайзеров
проваливают тест. Тесты не выключают проверку утечек и не подавляют отчёты.
