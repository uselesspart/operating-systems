# Лабораторная работа №2. Межпроцессное взаимодействие (вариант 3)

Межпроцессное взаимодействие в системе Linux. Реализованы три вида IPC
(очереди сообщений, именованные каналы, сокеты) для сценария "Волк и
семеро козлят" в конфигурации "Родственные. Один к одному". Хост - Qt GUI,
клиент - процесс-потомок, порождённый через `fork()`. Синхронизация -
локальными POSIX-семафорами в разделяемой памяти.

**Сценарий 1**: "Волк и семеро козлят"
**Конфигурация**: Родственные. Один к одному.
**Типы взаимодействия**: 4 (`mq`), 6 (`fifo`), 7 (`sock`)

## Требования

- Linux (POSIX-совместимая система).
- Компилятор с поддержкой C++17: `g++` 9+ или `clang++` 10+.
- `cmake` 3.10+.
- Qt5 (`qtbase5-dev`).
- Графическая сессия (X11 или Wayland с XWayland).

Установка зависимостей:

```sh
sudo apt update
sudo apt install -y cmake g++ qtbase5-dev
```

Для запуска Qt-приложения может потребоваться запуск из системного терминала из-за конфликта библиотек Snap.

## Сборка

Перед первым запуском выдайте скриптам права на исполнение:

```sh
chmod +x build.sh tests.sh tests/run_unit_tests.sh tests/integration/run.sh
```

Сборка выполняется скриптом build.sh. Скрипт вызывает make clean, make и удаляет промежуточный каталог build/. 
Цели make описаны в Makefile, реальная сборка через CMake.

```sh
./build.sh
```

Результат - три исполняемых файла в корне проекта, по одному на каждый
реализованный тип IPC:

| Файл | IPC | Тип |
|---|---|---|
| `host_mq` | `mq_open` | очереди сообщений POSIX |
| `host_fifo` | `mkfifo` | именованные каналы |
| `host_sock` | `socketpair` | Unix-сокеты (`SOCK_SEQPACKET`) |

Скрипт автоматически находит все `src/conn_*.cpp` через `file(GLOB ...)`
в `CMakeLists.txt`. Для каждого файла создаётся target `host_<TYPE_CODE>`
с макросами `CONN_HEADER` и `CONN_CLASS`, что позволяет использовать один
`src/host.cpp` для всех типов.

## Правила игры

**Участники.** Хост - волк, клиент - козлёнок (один, так как конфигурация
"один к одному").

**Раунд:**

1. Волк выбирает число от 1 до 100. Пользователь вводит его в диалоге;
   если за 3 секунды число не введено - выбирается случайно.
2. Козлёнок бросает число:
   - 1–100, если он жив;
   - 1–50, если он мёртв.
3. Логика (реализована в хосте):
   - живой козлёнок: `|волк − козлёнок| ≤ 70` -> спрятался (остаётся жив);
   - иначе - пойман (становится мёртв);
   - мёртвый козлёнок: `|волк − козлёнок| ≤ 20` -> воскрес;
   - иначе - остаётся мёртв.

**Завершение.** Игра заканчивается, если козлёнок мёртв два раунда подряд.
В конфигурации "один к одному" клиент порождается через fork() при старте хоста, поэтому игра начинается сразу.

**Отображение.** В окне хоста видны: номер раунда, число волка, число
козлёнка, статус козлёнка (спрятался / пойман / воскрес / остался мёртв),
а также счётчики спрятавшихся, пойманных и воскресших, и текущий статус ("Жив: да/нет").

## Запуск

Выберите любой из трёх бинарников - поведение игры идентично, отличается
только транспорт.

```sh
./host_mq      # очередь сообщений
./host_fifo    # именованные каналы
./host_sock    # Unix-сокеты
```

Порядок:

1. Открывается окно Qt "Волк и козлёнок (lab2, вариант 3)".
2. В логе появляются строки "Хост запущен" и "Клиент (козлёнок) присоединился".
3. Открывается модальный диалог "Ход волка" с полем ввода и обратным
   отсчётом 3 секунды.
4. Введите число 1–100 и нажмите Enter (или подождите 3 секунды -
   число выберется случайно).
5. В логе появляется строка раунда, сразу открывается следующий диалог.
6. Игра завершается автоматически после двух смертей подряд. В логе появляется "ИГРА ЗАВЕРШЕНА".

**Предупреждение.** При запуске в stderr может появиться:

```
QSocketNotifier: Can only be used with threads started with QThread
```

Это безвредное предупреждение Qt, связанное с тем, что `fork()` выполняется
до инициализации `QApplication` - так требует задание (клиент должен быть
ребёнком хоста). На работу не влияет: окно открывается, игра идёт, IPC
функционирует. Предупреждение можно игнорировать

**Проверка, что хост создал процесс клиента:**

```sh
ps -ef | grep host_mq | grep -v grep
```

Должно быть **два** процесса: родитель (Qt GUI) и ребёнок (козлёнок).
У ребёнка `PPID` равен PID родителя.

**Запуск из VS Code.** Если VS Code установлен через Snap, запуск
`./host_mq` из его встроенного терминала может завершиться ошибкой
`symbol lookup error: ... undefined symbol: __libc_pthread_init`. Это
конфликт библиотек Snap-окружения с системной `glibc`, к коду отношения
не имеет. Запускайте из системного терминала (`Ctrl+Alt+T`) или очистите
переменные:

```sh
env -u GTK_PATH -u GIO_MODULE_DIR ./host_mq
```

## Логирование

Хост пишет статусные сообщения в **графический интерфейс** (`QTextEdit`):
запуск, присоединение клиента, каждый раунд, завершение игры. Клиент
(ребёнок-козлёнок) пишет в **системный журнал** (`syslog`) с тегом
`lab2_client` - ошибки IPC, отправленные числа, полученные статусы.

### Просмотр логов клиента во втором терминале

Удобно открыть **второй терминал** и в нём смотреть поток сообщений
клиента в реальном времени, пока игра идёт в первом:

**Терминал 1** - запуск игры:

```sh
cd ~/Projects/os-fork/Zhitkov.Nikita/lab2
./host_mq
```

**Терминал 2** - живой журнал клиента:

```sh
journalctl -t lab2_client -f
```

Пока играете, во втором терминале будут появляться строки:

```
lab2_client[PID]: round: kid_num=42 (alive=1)
lab2_client[PID]: round result: kid_alive=1
lab2_client[PID]: round: kid_num=83 (alive=1)
lab2_client[PID]: round result: kid_alive=0
lab2_client[PID]: round: kid_num=17 (alive=0)
lab2_client[PID]: round result: kid_alive=1
```

Если клиент не может прочитать или отправить сообщение, вместо `round`
появится ошибка:

```
lab2_client[PID]: timeout waiting for host message
lab2_client[PID]: read from host failed
lab2_client[PID]: write kid number to host failed
```

После последней строки клиент завершается. Окно хоста остаётся открытым - закройте его крестиком вручную.

### Последние N строк без подписки

Если не хочется держать `-f`, можно посмотреть последние записи:

```sh
journalctl -t lab2_client -n 30 --no-pager
```

### Unit-тесты (`tests/src/`)

| Файл | Область | Что проверяет |
|---|---|---|
| `test_scenario.cpp` | Логика игры | hid / caught / resurrected, границы `70` и `20`, `game over` после двух смертей подряд, сброс счётчика при воскрешении, суммарные счётчики |
| `test_protocol.cpp` | Протокол | `sizeof(HostToClient) == 8`, `sizeof(ClientToHost) == 8`, round-trip `memcpy` обеих структур |
| `test_sems.cpp` | Семафоры | `sem_timedwait` возвращает `false` по истечении таймаута; `pshared=1` - `sem_post` из другого процесса будит ожидающего |

### Интеграционные тесты (`tests/integration/`)

Каждый тест форкает ребёнка, обменивается тремя сообщениями через реальный IPC-механизм и проверяет содержимое на обеих сторонах.

| Файл | Что проверяет |
|---|---|
| `test_conn_mq.cpp` | `ConnMq::createHost` / `createClient`, `mq_send` / `mq_receive`, `sem_post` из ребёнка будит родителя |
| `test_conn_fifo.cpp` | `ConnFifo::createHost` / `createClient` через `mkfifo`, обмен по двум FIFO, `unlink` при закрытии |
| `test_conn_sock.cpp` | `ConnSock::preFork` (создаёт `socketpair` до fork), `send` / `recv` через `SOCK_SEQPACKET` |

## Архитектурные решения

**Единый интерфейс `Conn`.** Базовый класс `Conn` объявляет `Read` / `Write`,
наследники (`ConnMq`, `ConnFifo`, `ConnSock`) реализуют транспорт. Хост и
клиент работают с абстракцией - конкретный IPC подставляется на этапе
линковки через макросы `CONN_HEADER` / `CONN_CLASS`.

**Автогенерация хостов.** `CMakeLists.txt` через `file(GLOB ...)` находит
все `src/conn_*.cpp` и для каждого создаёт target `host_<TYPE_CODE>` с
`-DCONN_HEADER=\"ConnXxx.h\" -DCONN_CLASS=ConnXxx`. Добавление нового IPC -
это создание `src/conn_<новый>.cpp` и `include/Conn<Новый>.h`, без правки
`CMakeLists.txt` и `host.cpp`.

**Родственная конфигурация.** Хост вызывает `fork()`, ребёнок становится
клиентом. Знакомство не требуется (тип "Без знакомства" из задания) -
после `fork()` оба процесса уже знают друг о друге через наследованные
ресурсы.

**Локальные семафоры.** `sem_init(&sem, pshared=1, 0)` в
`mmap(MAP_SHARED|MAP_ANONYMOUS)` до `fork()`. После `fork()` оба процесса
видят одну и ту же область памяти и работают с одними и теми же семафорами.
Два семафора - `host_msg_ready` и `client_msg_ready` - обеспечивают
строгую очередность "хост отправил -> клиент прочитал -> клиент ответил ->
хост прочитал".

**Таймауты.** Все ожидания семафоров через `sem_timedwait` с лимитом 5
секунд (`semWaitTimeout`). При превышении таймаута хост завершает игру с
сообщением об ошибке; клиент завершается сам.

**Привязка ресурсов к жизненному циклу процесса.** Для `mq` очереди
создаются в `preFork()` (до `fork`), чтобы клиент мог открыть их сразу
после форка. Для `fifo` файлы `mkfifo` тоже создаются до fork. Для
`socketpair` пара дескрипторов создаётся до fork, каждый процесс забирает
свой конец. Деструкторы (`~ConnMq`, `~ConnFifo`) вызывают `mq_close` /
`mq_unlink` / `unlink` - ресурсы удаляются при корректном завершении
родителя.

**Чистая игровая логика.** `Scenario` не знает про IPC, Qt и процессы -
принимает два числа и возвращает статус раунда. Это позволяет покрыть всю
игровую логику юнит-тестами без запуска хоста.

**Qt только в хосте.** Клиент (`ClientLoop`) - обычный C++-цикл без
зависимости от Qt. Он запускается в ребёнке после `fork()`, до того как
родитель вызывает `QApplication`. Это исключает проблемы с наследованием
состояния Qt через `fork`.

**Форк до Qt.** `fork()` происходит **до** `QApplication`, поэтому ребёнок
не наследует никакого состояния Qt и может спокойно работать без него.
Если бы порядок был обратный, ребёнку пришлось бы либо вызывать
`QCoreApplication::exec()` внутри себя (лишний цикл событий), либо
аккуратно избегать любых Qt-вызовов - оба варианта сложнее.
