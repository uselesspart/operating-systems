# Лабораторная работа №1. Демон Напоминалка (вариант 19)

Демон-напоминалка для Linux. Периодически опрашивает файл событий и по наступлении времени открывает новый терминал с заданным текстом. Реализован на C++17 с использованием POSIX API (`fork`, `setsid`, `syslog`, сигналы).

## Требования

- Linux (POSIX-совместимая система).
- Компилятор с поддержкой C++17: `g++` 7+ или `clang++` 5+.
- Графическая сессия (X11 или Wayland с XWayland) для отображения напоминаний.
- Один из терминалов: `gnome-terminal`, `konsole`, `xfce4-terminal`, `mate-terminal`, `xterm`.
- Утилита `zenity` (опционально) — резервный способ показать напоминание.
- `systemd-run` (опционально) — используется первым в цепочке для `gnome-terminal`, чтобы корректно отработать в контексте пользовательской сессии.

Для чтения системного журнала дополнительно требуется `journalctl` (systemd) либо доступ на чтение `/var/log/syslog`.

## Сборка

Перед первым запуском выдайте скриптам права на исполнение:

```sh
chmod +x build.sh add_event.sh test.sh tests/unit_tests/run.sh tests/integration_tests/run.sh
```

Сборка выполняется скриптом `build.sh`. Скрипт компилирует исходники с
флагами `-Wall -Werror`, линкует их в один исполняемый файл
`reminder_daemon` и удаляет промежуточные объектные файлы.

```sh
./build.sh
```
Результат: исполняемый файл `reminder_daemon` в корне проекта.

Скрипт поддерживает переменную окружения `CXX` для указания компилятора:

```bash
CXX=clang++ ./build.sh
```

## Конфигурация

Файл `reminder.conf` располагается в корне проекта. При запуске демон определяет его абсолютный путь через `realpath()` и использует этот путь до завершения процесса. По сигналу `SIGHUP` конфиг перечитывается.

Формат файла:

```conf
interval = 10
events_file = events.txt
```

| Параметр | Тип | Описание |
|---|---|---|
| `interval` | целое положительное число | Период опроса файла событий в секундах. |
| `events_file` | строка | Путь к файлу событий. Абсолютный или относительный — во втором случае разрешается относительно каталога, содержащего конфиг. |

При ошибке разбора конфига (отсутствие файла, отсутствие обязательного параметра, нечисловое или неположительное значение `interval`) демон записывает сообщение в системный журнал и завершается с кодом возврата `1`.

## Управление событиями

События добавляются скриптом `add_event.sh`.

```
./add_event.sh <DD.MM.YYYY> <HH:MM:SS> [-h|-d|-w] <text>
```

| Аргумент | Обязателен | Описание |
|---|---|---|
| `DD.MM.YYYY` | да | Дата напоминания. |
| `HH:MM:SS` | да | Время напоминания. |
| `-h` | нет | Повторять каждый час. |
| `-d` | нет | Повторять каждый день. |
| `-w` | нет | Повторять каждую неделю. |
| `text` | да | Текст напоминания. |

Если флаг не указан, событие считается одноразовым.

Примеры:

```bash
./add_event.sh 31.12.2025 23:59:00 -d Happy New Year
./add_event.sh 01.01.2025 09:00:00 "Morning standup"
./add_event.sh 15.06.2025 12:00:00 -w "Weekly report"
```

Скрипт проверяет формат даты и времени, добавляет запись в файл событий и отправляет работающему демону сигнал `SIGHUP`, чтобы тот перечитал конфигурацию.

Запись в файле событий имеет вид:

```
DD.MM.YYYY HH:MM:SS [-h|-d|-w] text
```

Пример содержимого `events.txt`:

```
31.12.2025 23:59:00 -d Happy New Year
01.01.2025 09:00:00 Morning standup
15.06.2025 12:00:00 -w Weekly report
```

Путь к конфигу можно переопределить переменной окружения `REMINDER_CONFIG`:

```bash
REMINDER_CONFIG=/etc/reminder/reminder.conf ./add_event.sh ...
```

## Запуск и завершение

### Запуск (два терминала)

Чтобы увидеть демон в работе, нужны **два терминала**: один для запуска
демона, второй для просмотра журнала.

Откройте два окна. В **первом** терминале:

```bash
cd /path/to/Zhitkov.Nikita/lab1   # перейти в корень проекта
./build.sh                        # сборка
./reminder_daemon reminder.conf   # запуск демона (подробнее далее)
echo "exit: $?"
```

Демон уходит в фон, команда сразу возвращает управление, `exit: 0`.

**Во втором** терминале открой поток журнала — сюда будут приходить все
сообщения демона (подробнее далее):

```bash
journalctl -t reminder_daemon -f
```

Вернитесь в **первый** терминал и добавьте событие через 10 секунд:

```bash
./add_event.sh "$(date '+%d.%m.%Y')" "$(date -d '+10 seconds' '+%H:%M:%S')" "Тест"
```

**Через 10 секунд:**

- во **втором** терминале (журнал) появится:
  ```
  reminder_daemon[...]: Сработала напоминалка: Тест
  ```
- **на экране откроется окно** с текстом:
  ```
  Напоминалка

  Тест
  ```
  Окно висит, пока пользователь не закроет окно. Ввод с клавиатуры в нём
  отключён (`stty -echo`).

**Завершить демон** (первый терминал):

```bash
kill -SIGTERM "$(cat /tmp/reminder_daemon.pid)"
sleep 1
pgrep -a reminder_daemon           # пусто
cat /tmp/reminder_daemon.pid 2>&1  # No such file
```

Во **втором** терминале при этом появятся:

```
reminder_daemon[...]: Received signal 15, shutting down
reminder_daemon[...]: Daemon (pid=...) stopped
```

### Запуск демона

```bash
./reminder_daemon [path/to/reminder.conf]
```

Если путь не указан, используется `./reminder.conf`. Демон демонизируется,
создаёт pid-файл `/tmp/reminder_daemon.pid` и переходит в цикл опроса
файла событий.

Проверить, что демон запущен:

```bash
pgrep -a reminder_daemon        # одна строка с процессом
cat /tmp/reminder_daemon.pid    # PID демона
```

Если конфиг не найден или содержит ошибку, демон пишет в syslog
`Config load failed: ...` и завершается с кодом `1`.


### Открытие терминала

Демон открывает окно в графической сессии пользователя. Ему нужны переменные
`DISPLAY` и `XAUTHORITY`, поэтому запускать его следует из графического
терминала. Если `DISPLAY` не задан, напоминание пишется только в syslog
(`DISPLAY не задан; нельзя открыть терминал...`).

Терминал выбирается цепочкой через `sh -c '... || ... || ...'`, а не через
`execlp`. Каждый кандидат возвращает код возврата, и при ненулевом
управление переходит к следующему:

```
systemd-run --user --collect --quiet gnome-terminal -- ...
  || gnome-terminal -- ...
  || konsole -e ...
  || xfce4-terminal -e ...
  || mate-terminal -e ...
  || xterm -e ...
  || zenity --info --text ...
```

Это важно, потому что:

- `systemd-run --user` падает с ненулевым кодом, если у пользователя нет
  активного systemd-user сеанса (user bus) — цепочка переходит к
  следующему кандидату, а не «съедает» его через `execlp`;
- `gnome-terminal` может завершиться с кодом `0`, даже когда окно не
  открылось (он лишь клиент `gnome-terminal-server`) — поэтому последним
  звеном стоит `zenity`, который показывает GTK-диалог напрямую.

Если ни один терминал не запустился, напоминание всё равно зафиксировано
в syslog.

## Обработка сигналов

| Сигнал | Действие |
|---|---|
| `SIGHUP` | Перечитать конфигурационный файл. |
| `SIGTERM` | Записать в системный журнал сообщение о завершении, удалить pid-файл, завершить работу. |

Обработчики сигналов только выставляют флаги `volatile sig_atomic_t` — **два независимых**: `g_terminateFlag` (SIGTERM) и `g_reloadFlag` (SIGHUP). Основной цикл проверяет их: `g_terminateFlag` имеет приоритет и обрабатывается первым, поэтому `SIGHUP`, пришедший сразу за `SIGTERM`, не отменяет завершение. Вся содержательная работа (syslog, перечитывание конфига, fork) выполняется в основном цикле — это исключает вызов не реентерабельных функций из асинхронного контекста.

Примеры:

```bash
kill -SIGHUP  "$(cat /tmp/reminder_daemon.pid)"   # перечитать конфиг
kill -SIGTERM "$(cat /tmp/reminder_daemon.pid)"   # завершить работу
```

## Защита от повторного запуска

При старте демон выполняет следующие действия:

1. Проверяет, что `/tmp/reminder_daemon.pid` — обычный файл (`S_ISREG`) и принадлежит текущему пользователю (`st_uid == getuid()`). Симлинки и файлы чужого владельца игнорируются.
2. Читает PID из файла.
3. Проверяет, что процесс с этим PID существует и что это именно наш демон: читает `/proc/<pid>/comm` и сравнивает с `reminder_daemon`. Имя из `comm` берётся из ядра (`task_struct->comm`), его нельзя подделать через `argv[0]` - в отличие от `/proc/<pid>/cmdline`.
4. Если процесс существует и это `reminder_daemon`, отправляет ему `SIGTERM` и ожидает завершения до 5 секунд.
5. Если процесс не завершился, отправляет ему `SIGKILL`.
6. Выполняет демонизацию и записывает в pid-файл свой PID через `open(..., O_WRONLY|O_CREAT|O_TRUNC|O_NOFOLLOW, 0644)` с явным `fchmod(0644)`.

Это гарантирует, что:
- в системе работает не более одного экземпляра демона
- чужой процесс с PID из подложенного pid-файла не будет убит
- файл нельзя перезаписать через симлинк (`O_NOFOLLOW`)
- права `0644` не позволяют другим пользователям переписать pid-файл (в отличие от `0666`, который получался при `umask(0)` и `std::ofstream`)

## Системный журнал

Демон пишет сообщения через `openlog` / `syslog` / `closelog` с тегом `reminder_daemon` и уровнем `LOG_DAEMON`.

| Событие | Уровень | Сообщение |
|---|---|---|
| Запуск | `LOG_INFO` | `Демон запущен (config=...)` |
| Загрузка конфига | `LOG_INFO` | `Config loaded: interval=..., events_file=...` |
| Получение `SIGHUP` | `LOG_INFO` | `SIGHUP received, reloading config` |
| Ошибка конфига | `LOG_ERR` | `Config load failed: ...` |
| Срабатывание события | `LOG_INFO` | `Сработала напоминалка: <text>` |
| Пропущенное событие | `LOG_INFO` | `Skipping stale event (missed by N sec): <text>` |
| Отсутствие `DISPLAY` | `LOG_WARNING` | `DISPLAY не задан; нельзя открыть терминал. Сообщение: ...` |
| Завершение | `LOG_INFO` | `Daemon (pid=...) stopped` |

Просмотр журнала:

```bash
journalctl -t reminder_daemon -f
```

или

```bash
sudo tail -f /var/log/syslog | grep reminder_daemon
```

## Архитектурные решения

**Singleton для класса `Daemon`.** Демон существует в единственном экземпляре в системе, что отражено в архитектуре: `Daemon::instance()` возвращает ссылку на статический локальный объект, конструктор и операторы копирования закрыты.

**Двойной `fork`.** Демонизация выполняется через два вызова `fork` с `setsid` между ними. Это гарантирует, что демон не станет лидером сессии и не получит управляющий терминал.

**Отвязка от окружения.** После демонизации выполняется `chdir("/")`, закрываются все файловые дескрипторы, дескрипторы `0`, `1`, `2` перенаправляются в `/dev/null`.

**Обработка сигналов через флаг.** Обработчик сигнала только записывает номер сигнала в `volatile sig_atomic_t`. Основной цикл проверяет этот флаг и выполняет соответствующее действие. Это исключает вызов небезопасных функций из контекста обработчика.

**Grace-окно.** Событие срабатывает, если с момента наступления его времени прошло не более одного интервала опроса. Более старые события помечаются как пропущенные с записью в системный журнал. Это предотвращает веерное срабатывание накопившихся событий при запуске демона после простоя.

**Привязка к расписанию.** Для повторяющихся событий (`-h` / `-d` / `-w`) `fired_` хранит не момент, когда демон проснулся, а вычисленный `due` - момент, когда событие должно было сработать. Если демон отстал сильнее чем на `grace`, `decideEventAction` продвигает `due` на целое число периодов вперёд (`due += (now - due) / r * r`), сохраняя привязку к исходному расписанию. Так "каждый день в 9:00" остаётся в 9:00, даже если демон был выключен несколько дней. Решение вынесено в чистую функцию и покрыто юнит-тестом `testRecurringScheduleAlignment`.

**Модульная структура.** Заголовочные файлы располагаются в `include/`, реализации — в `src/`. Каждый модуль (`Config`, `Event`, `Daemon`) отвечает за свою область. Тесты следуют той же схеме.
