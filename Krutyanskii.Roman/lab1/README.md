# Лабораторная работа 1 — демон, вариант 14

Демон на C++, который каждые 20 секунд очищает содержимое указанных в конфиге
папок, если в них нет соответствующего «сторожевого» файла.

## Сборка

```sh
./build.sh
```

Скрипт компилирует все файлы из `src/` с флагами `-std=c++17 -Wall -Werror -O2`,
линкует их в один файл `lab1daemon` и удаляет промежуточные объектные файлы
(каталог `build/`) при выходе. Другой компилятор можно задать через `CXX`:

```sh
CXX=g++-11 ./build.sh
```

## Запуск

```sh
cp config/lab1.conf.example lab1.conf   # правите пути под себя
./lab1daemon                            # берёт lab1.conf из текущего каталога
./lab1daemon /etc/lab1daemon.conf       # либо явный путь
```

Конфиг ищется в рабочем каталоге запуска; программа запоминает его абсолютный
путь (`realpath`) до `chdir("/")` и дальше использует только этот путь.

После запуска команда возвращает управление сразу — демон работает в фоне.

## Формат конфигурационного файла

Произвольное число строк вида `folder ignfile` или `folder ignfile seconds`:

```
/tmp/lab1-scratch dont.erase
/tmp/lab1-reports keep.txt
/tmp/lab1-fast dont.erase 5
```

* если `ignfile` есть в `folder` — ничего не делаем;
* если `ignfile` отсутствует — рекурсивно удаляем всё содержимое `folder`
  (сама папка остаётся).

Пустые строки и строки, начинающиеся с `#`, игнорируются; любая другая строка
должна содержать два или три поля. При ошибке разбора действующая конфигурация
не заменяется — сломанный файл не может сломать работающий демон.

### Символьные ссылки

* Внутри `folder` симлинк **не обходится**, а удаляется: `lstat` + `unlink`,
  поэтому удаление содержимого папки не может уйти за её пределы. Ссылка,
  направленная на каталог, тоже просто удаляется — её цель остаётся целой.
* Сам `folder` из конфига, наоборот, разыменовывается: если это ссылка на
  каталог, очищается каталог-цель, а сама ссылка сохраняется. Так поведение
  совпадает с проверкой `ignfile` и с `rm -rf folder/*`. О таком случае в журнал
  пишется отдельное сообщение, чтобы очистка не выглядела незаметной.

### Интервал

Вариант 14 задаёт интервал 20 секунд, и это значение стоит по умолчанию
(`kScanIntervalSeconds`, `src/common.h`). Общая часть условия требует, чтобы
интервал задавался в конфигурационном файле, поэтому третьим полем его можно
переопределить для конкретного правила: `folder ignfile seconds`. Демон
просыпается каждые `min` из интервалов и обрабатывает правило, когда с момента
его прошлой обработки прошёл именно его интервал. Допустимое значение — целое
число секунд от 1 до 86400, иначе строка считается ошибочной.

## Управление

| Действие | Команда |
| --- | --- |
| Перечитать конфиг | `kill -HUP $(cat /tmp/lab1daemon.pid)` |
| Остановить | `kill -TERM $(cat /tmp/lab1daemon.pid)` |
| Журнал | `journalctl -t lab1daemon -f` или `tail -f /var/log/syslog` |

`SIGHUP` перечитывает конфигурационный файл, `SIGTERM` пишет в журнал сообщение
о выходе и завершает работу. `SIGINT` обрабатывается так же, как `SIGTERM`,
чтобы демон можно было остановить из терминала по `Ctrl+C`.

## Защита от повторного запуска

Pid-файл — `/tmp/lab1daemon.pid` (путь в `kPidFilePath`, `src/common.h`).
Выбран `/tmp`, а не `/var/run`, потому что последний доступен для записи только
root: демон должен запускаться без повышения прав. Файл открывается с
`O_NOFOLLOW`, поэтому подложенная кем-то ссылка в общем каталоге не приведёт к
усечению чужого файла.

При старте новый процесс читает pid-файл и проверяет через `/proc`, что такой
процесс существует и что это именно тот же исполняемый файл (сверка
`/proc/<pid>/exe` — защита от переиспользования pid). Если да, старому процессу
отправляется `SIGTERM`, и новый ждёт его завершения до 5 секунд. Если старый
экземпляр за это время не умер, новый **не стартует** и возвращает ненулевой
код возврата: демон по смыслу своему один, и молча запустить второй значило бы
получить две копии, чистящие одни и те же папки. Свой pid новый процесс
записывает уже после демонизации. Устаревший, повреждённый или непригодный
pid-файл игнорируется с записью в журнал.

Код возврата запускающего процесса соответствует реальному результату: ребёнок
докладывает стартовщику об успехе через `pipe` до выхода, поэтому ошибка уже
после `fork()` (например, не удалось записать pid-файл) не выглядит для вызывающей
стороны как успех.

## Журнал

Всё пишется через `openlog` / `syslog` / `closelog` с идентификатором
`lab1daemon` (`kLogIdent`): старт, перезагрузка конфига, действия над папками,
ошибки, выход.

## Структура

```
lab1/
├── build.sh                      сборка
├── config/lab1.conf.example      пример конфига
└── src/
    ├── main.cpp                  разбор аргументов, точка входа
    ├── daemon.h / daemon.cpp     синглтон-демон: fork, сигналы, pid-файл, цикл
    ├── config.h / config.cpp     разбор конфигурационного файла
    ├── fileops.h / fileops.cpp   рекурсивное удаление содержимого папки
    ├── logger.h / logger.cpp     обёртка над openlog/syslog/closelog
    └── common.h / common.cpp     константы и общие мелочи
```
