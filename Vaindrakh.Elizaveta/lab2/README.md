# Лабораторная работа № 2. Межпроцессное взаимодействие. Вариант 1

Реализован **вариант 1**: игра «Волк и семеро козлят», родственные процессы, один хост и один клиент. Язык C++17, графический интерфейс хоста — Qt Widgets, целевая система — Linux. На этом компьютере программа собирается и запускается в Ubuntu-24.04 через WSL.

Исходное [условие на GitHub](https://github.com/uselesspart/operating-systems/blob/main/2.%20%D0%9C%D0%B5%D0%B6%D0%BF%D1%80%D0%BE%D1%86%D0%B5%D1%81%D1%81%D0%BD%D0%BE%D0%B5%20%D0%B2%D0%B7%D0%B0%D0%B8%D0%BC%D0%BE%D0%B4%D0%B5%D0%B9%D1%81%D1%82%D0%B2%D0%B8%D0%B5/lab2.md) сохранено также в `docs/assignment.md`.

## Быстрый запуск в Windows

Откройте **start.cmd** двойным щелчком и выберите способ связи: 1 — mmap, 2 — shm, 3 — pipe. При первом запуске скрипт соберёт Linux-программы в установленной Ubuntu-24.04 через WSL. Затем откроется окно игры на русском языке. Для повторной сборки и запуска всех тестов откройте **test.cmd**. Готовые программы и временные файлы сборки в Git не включаются.

## Сборка и запуск в Linux / WSL

Зависимости Ubuntu:

```bash
sudo apt-get update
sudo apt-get install build-essential cmake qt6-base-dev python3
```

В каталоге работы:

```bash
make
./host_mmap
# либо ./host_shm, либо ./host_pipe
make test
```

`make` вызывает `build.sh`, который собирает все `host_*` во временном каталоге, копирует готовые программы в каталог проекта и удаляет промежуточные файлы CMake при успехе и при ошибке. `make test` дополнительно собирает и запускает тесты. `BUILD_JOBS=4 make` меняет число параллельных задач сборки. `make clean` удаляет три готовые программы.

Для отладки можно сохранить отдельный каталог сборки:

```bash
cmake -S . -B build -DBUILD_TESTING=ON
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure
```

## Правила и управление

В названии сценария семь козлят, но конфигурация варианта 1 требует **одного клиента**, поэтому в расчётах **n = 1**. Хост вызывает `fork()` ровно один раз. Клиент — отдельный процесс-козлёнок, отдельная программа `client_*` для этой конфигурации не требуется.

Игра начинается после сообщения готовности клиента. На каждом ходу введите число волка от 1 до 100 и нажмите «Сделать ход» или Enter. Через 3 секунды без подтверждения число выбирается случайно. Клиент случайно выбирает число 1–100, пока жив, и 1–50, пока мёртв. Хост определяет результат:

- живой козлёнок прячется при `abs(wolf - goat) <= 70`, иначе погибает;
- мёртвый козлёнок воскресает при `abs(wolf - goat) <= 20`;
- игра завершается после двух последовательных ходов, в конце которых козлёнок мёртв; воскрешение сбрасывает этот счётчик.

В таблице отображаются числа обоих участников, спрятавшиеся, попавшиеся, воскресшие и мёртвые козлята. Ниже отображаются сообщения о подключении, ходе игры, завершении и ошибках. Новая игра запускается повторным открытием программы. Кнопка «Завершить и закрыть» останавливает клиента и закрывает окно.

## Три способа связи

| Программа | Реализация | Момент создания |
|---|---|---|
| `host_mmap` | `mmap(MAP_SHARED \| MAP_ANONYMOUS)` | Общая область создаётся до `fork`, наследуется ребёнком |
| `host_shm` | `shm_open` + `ftruncate` + `mmap` | Обе стороны открывают и отображают объект уже после `fork` |
| `host_pipe` | Два анонимных `pipe2` для двух направлений | Создаются до `fork`, лишние концы закрываются в обоих процессах |

Во всех случаях используются локальные безымянные семафоры `sem_init(..., pshared=1, ...)`, размещённые в наследуемой анонимной общей памяти. В `shm` отдельный семафор готовности позволяет ребёнку дождаться создания объекта родителем. Это синхронизация родственных процессов; знакомства через сигналы в варианте 1 нет.

Каждое ожидание семафора ограничено 5 секундами. Повтор после `EINTR` сохраняет исходный срок. Каналы неблокирующие, операции чтения/записи используют `poll` с ограничением времени. При явном закрытии канала ошибка может определиться раньше 5 секунд. При ошибке клиент завершает работу, хост прекращает игру и выводит причину. Отдельный рабочий поток хоста выполняет IPC, пока основной поток обслуживает окно Qt.

## Протокол и освобождение ресурсов

```text
Клиент -> Ready(0)
Хост   -> Roll(номер хода, текущее состояние)
Клиент -> Number(номер хода, число)
Хост   -> Status(номер хода, жив/мёртв, завершение)
Клиент -> Ready(номер хода) или Bye(номер хода)
```

Подтверждение после `Status` обязательно: оно исключает перезапись единственного слота общей памяти следующим сообщением. Стороны проверяют тип сообщения, номер хода, состояние и диапазон чисел. В конце игры хост получает `Bye`, затем забирает код завершения ребёнка через `waitpid`. При закрытии окна посылается `Stop`. Если ребёнок не завершился за 2 секунды, хост завершает его принудительно и обязательно выполняет `waitpid` перед уничтожением семафоров. `SIGINT`/`SIGTERM` обрабатываются хостом с тем же освобождением ресурсов. Как обычно в Linux, перехватить `SIGKILL` невозможно; аварийное убийство самого хоста этим сигналом не гарантирует удаление именованного объекта.

Дескрипторы закрываются, отображения освобождаются через `munmap`, объект `/wolf_lab2_<pid>` удаляется создавшим его хостом через `shm_unlink`. Одновременные запуски используют разные имена по PID. Журнал по умолчанию — `lab2_mmap.log`, `lab2_shm.log` или `lab2_pipe.log`; каждая запись содержит время в миллисекундах Unix и PID процесса. Путь можно задать через `--log`.

## Автоматические тесты

`make test` запускает 8 наборов CTest:

- `game`: все 15 000 допустимых пар чисел для живого/мёртвого козлёнка, граничные значения 70/71 и 20/21, воскрешение, два мёртвых хода подряд, недопустимые значения;
- `ipc_mmap`, `ipc_shm`, `ipc_pipe`: по 1000 обменов между настоящими процессами, целостность сообщений, пятисекундный тайм-аут с прерыванием сигналом, удаление общей памяти;
- `gui_mmap`, `gui_shm`, `gui_pipe`: окно Qt, ожидание подключения, ручной ход нажатием кнопки, автовыбор через 3 секунды, таблица, конечный статус и завершение ребёнка; тесты запускаются с `QT_QPA_PLATFORM=offscreen`;
- `integration`: 9 сценариев Python `unittest`, каждый проверяет все три реализации, включая воскрешение, случайные диапазоны и повторяемость, некорректные аргументы, недоступный журнал, убийство клиента, сигнальное завершение хоста, остановку хоста с самостоятельным завершением клиента через 5 секунд.

В тестах не используется `assert`, который мог бы исчезнуть в Release-сборке. Тестовые последовательности передаются ребёнку через память, унаследованную при `fork`; числа козлёнка по-прежнему отправляет именно дочерний процесс по выбранному IPC.

Детерминированная демонстрация без окна:

```bash
./host_mmap --headless --wolf-sequence 100,21,100,100 --goat-sequence 1,1,1,1
./host_shm --headless --seed 42 --round-limit 50
./host_pipe --help
```

Без `--headless` используется окно и фиксированные 3 секунды на ввод. `--delay-ms` относится только к запуску без окна. Опции `--wolf-sequence` и `--goat-sequence` предназначены для проверки; после конца последовательности используются случайные значения. `--round-limit` — необязательный предел для демонстраций, в обычной игре его нет.

## Структура исходников

`src/host.cpp` содержит `main` хоста. `src/client_worker.cpp` выполняется в дочернем процессе. `src/game.cpp` содержит правила, `src/session.cpp` — управление процессом и протоколом, `src/window.cpp` — окно. `src/conn_mmap.cpp`, `src/conn_shm.cpp`, `src/conn_pipe.cpp` реализуют общий интерфейс `Connection` с `Read`, `Write` и `afterFork`. Заголовки расположены в `include/`, тесты — в `tests/`.

CMake автоматически подхватывает `.cpp` и `.c` из `src/`. Новый `src/conn_TYPE.cpp` или `src/conn_TYPE.c` с той же фабрикой и интерфейсом C++ автоматически создаёт `host_TYPE`; менять CMakeLists не нужно. Файлы транспорта с расширением `.c` также компилируются как C++, поскольку реализуют классы общего интерфейса. Все исходники собираются с `-Wall -Wextra -Werror`. `QApplication` и потоки создаются только после `fork`.

Работа размещается в каталоге `Vaindrakh.Elizaveta/lab2` форка репозитория, как требует общий README курса. В этой папке находятся исходники, тесты, файлы сборки и документация. Pull request оформляется отдельно.
