# Лабораторная работа № 2. Вариант 1

## Цель работы

Освоить межпроцессное взаимодействие в Linux: создание родственного процесса через `fork`, обмен через общую память и программные каналы, синхронизацию безымянными семафорами и управление жизненным циклом процессов.

## Постановка задачи

Реализовать сценарий «Волк и семеро козлят» в конфигурации «родственные, один к одному». Хост отвечает за игровую логику и графическое отображение, дочерний клиент генерирует числа козлёнка. Требуются три независимые реализации транспорта: анонимный `mmap`, `shm_open` с `mmap` и `pipe`. Сборка должна выполняться через Makefile и CMake с `-Wall -Werror`, тесты обязательны.

## Принятые решения

Количество козлят в варианте равно одному: один хост порождает ровно один дочерний процесс. Поэтому пороги `70/n` и `20/n` равны 70 и 20. Дочерний процесс не запускает окно и не вычисляет игровой результат — он получает состояние, генерирует допустимое число и передаёт его хосту. Вся логика состояния находится в классе `Game`.

Общий интерфейс `Connection` включает `afterFork`, `Read`, `Write` и виртуальный деструктор. Каждый файл `conn_TYPE.cpp` содержит свой класс и фабрику `createConnection`. Остальная программа использует этот интерфейс независимо от выбранного транспорта. CMake автоматически обнаруживает файлы транспорта и создаёт соответствующие исполняемые программы.

Анонимная память и каналы создаются до `fork`, поскольку ребёнок наследует эти ресурсы. POSIX-объект общей памяти обе стороны открывают и отображают уже после `fork`, как предписано условием. Родитель сигнализирует о готовности объекта через безымянный семафор. Идентификатор объекта включает PID создавшего его хоста.

## Синхронизация и протокол

Семафоры создаются через `sem_init` с `pshared = 1` в анонимной общей памяти. Два семафора соответствуют направлениям обмена, третий используется только для подготовки `shm`. Ожидание выполняется через `sem_timedwait` с абсолютным сроком через 5 секунд. Прерывание сигналом не пересоздаёт срок.

После подключения клиент передаёт `Ready`. Для каждого хода хост посылает `Roll`, клиент отвечает `Number`, хост возвращает `Status`, клиент подтверждает его через `Ready` или `Bye`. Подтверждение не позволяет хосту записать следующее сообщение до чтения предыдущего клиентом. В сообщениях проверяются тип, номер хода и допустимые значения. `Stop` завершает клиент при закрытии окна.

Для `pipe` используются два канала, чтобы разделить направления обмена. Неиспользуемые концы закрываются сразу после `fork`. Неблокирующие дескрипторы и `poll` обеспечивают ограниченное ожидание и обработку неполных операций чтения/записи.

## Интерфейс и алгоритм

Окно Qt показывает состояние подключения, поле числа волка, оставшееся время, историю ходов и журнал событий. На ввод выделяется 3 секунды. Если число не подтверждено, запускается случайный выбор. IPC выполняется в рабочем потоке, а обновление окна — в основном потоке через очередь Qt. `fork` вызывается до создания `QApplication` и потоков.

Для живого козлёнка условие укрытия — `abs(wolf - goat) <= 70`; для мёртвого условие воскрешения — `abs(wolf - goat) <= 20`. После каждого хода счётчик последовательных мёртвых состояний увеличивается либо сбрасывается. При достижении двух игра завершается.

## Завершение и ошибки

Все ошибки системных вызовов превращаются в сообщения с названием операции и причиной. Клиент завершает работу при тайм-ауте или ошибке протокола. Хост показывает ошибку в окне и сохраняет её в журнал. При завершении хост забирает статус ребёнка через `waitpid`, после чего закрываются дескрипторы, освобождаются отображения и семафоры; созданный POSIX-объект удаляется через `shm_unlink`.

## Вывод

Реализованы и проверены все три вида IPC из варианта 1. Единый интерфейс транспорта позволил использовать одинаковую игровую логику и интерфейс Qt. Безымянные семафоры задают порядок обмена, подтверждения защищают общие слоты от перезаписи, ограниченные ожидания предотвращают бесконечную блокировку при отказе второй стороны.
